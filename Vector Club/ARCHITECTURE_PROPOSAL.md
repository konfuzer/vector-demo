# Vector Club — архитектура локального демо

Статус на 23.10.2026: реализовано после отдельного прямого разрешения пользователя продолжить разработку. Документ начат как предложение после одобрения макетов и обновлён по результату. Приложение, зависимости и сервер существуют. Запись ограничена папкой `Vector Club/`. Flow, Universe, Hub и корень не менялись.

## 1. Результат и состав

Одно самостоятельное приложение Club с родительскими экранами и собственной админкой. Они используют один демонстрационный набор и одни правила изменения данных. Между режимами есть явно обозначенный переключатель демонстрации; это не настоящая авторизация.

| Поверхность | Представления и действия |
|---|---|
| Родитель | Каталог, комбинируемые фильтры и сброс, программа, выбор конкретной группы |
| Заявка в группу | Форма с сохранённым выбором и сводкой условий; отдельное подтверждение отправки |
| Обращение на подбор | Форма без обязательной программы/группы: возраст, интересы, дни, контакт |
| Статус | Получение заявки, предложенные варианты, выбор группы родителем, бронь, отметка оплаты либо закрытие с причиной |
| Администратор | Обращения со списком и подробностями, подбор вариантов, контакт, бронь, демонстрационная оплата и отмена неоплаченной брони |
| Группы и программы | Каталог групп, условия, ёмкость и состав; доступность относится к группе |
| Полный редактор | Создание программы, название, возраст, категория, описание, пункты содержания, обложка, заголовок карточки и цвет текста; несколько групп с отдельными условиями |
| Главная и график | Порядок программ и три позиции первого экрана; редактируемые рабочие дни и время для футера |
| Итоги | Поступления за период и текущая загрузка; отдельный сценарный прогноз |
| Помощник | Маленькая кнопка приглашения, большая закрываемая панель с фиксированным примером диалога и переход к форме |

Для помощника нет модели, API, свободного ввода и сетевых запросов. Подпись «Демонстрация подбора» и текст «Пример диалога · без AI-модели» сохраняются. Кнопка перехода к форме работает как обычная навигация; диалог сам заявку не создаёт. При переносе пожеланий явно указать, что это данные демонстрационного примера.

Полноценная CRM, LMS, оценки, преподавательский кабинет, аккаунты, настоящие платежи, уведомления и связи с Flow не входят в этот запуск.

## 2. Технологии и визуальное исполнение

- React + TypeScript + Vite; собственный `package.json` и lock-файл внутри Club. Зависимости не навязывают стек соседним продуктам.
- Авторские CSS/CSS Modules, общие токены палитры, типографики, отступов и состояний элементов. Библиотека готовых административных компонентов не нужна.
- Состояние реализовано через React Context и чистую функцию бизнес-команд `applyCommand`; синхронная ссылка на последнее состояние защищает повторные действия до следующей перерисовки. Производные показатели вычисляются из записей, а не хранятся как независимые изменяемые счётчики.
- Навигация между несколькими экранами может использовать hash-маршруты с небольшой локальной реализацией, без серверной маршрутизации. Кнопки браузера назад/вперёд должны работать; маршруты проверяются на существующие сущности.
- Объём и материалы одобренных обложек реализуются подготовленными растровыми ассетами. Сами формы, заголовки, фильтры, карточки и кнопки — настоящие элементы интерфейса; цельный скриншот страницы вместо приложения не используется.
- Точный знак — `assets/brand/vektor-official.png`, с сохранением пропорций. Генерация логотипа исключена. Исходный официальный SVG сохраняется рядом.
- FuturaPT указан в сохранённых наблюдениях официального сайта; перед подключением проверить фактический файл и отображение. Допустимый локальный шрифт или визуально близкий вариант подбирается с проверкой макета. Не полагаться на то, что нужный шрифт уже установлен у пользователя.
- После подготовки локальные ассеты и шрифты не зависят от доступности внешних сайтов во время показа. Чужие страницы и фотографии детей из отвергнутых референсов не используются.
- Vitest — для правил мест, статусов, оплаты, дублей и сброса; Playwright — для сквозных браузерных сценариев и скриншотов. Это проверки после реализации, не уже выполненные тесты.

При подготовке предложения проверены официальные источники: [Vite](https://vite.dev/guide/), [React: reducer и context](https://react.dev/learn/scaling-up-with-reducer-and-context), [Vitest](https://vitest.dev/guide/), [Playwright](https://playwright.dev/docs/intro). После разрешения установки версии зафиксированы в собственном `package-lock.json`; общих зависимостей нет.

## 3. Данные и операции

| Сущность | Назначение |
|---|---|
| Программа | Название, описание, направление, возраст, локальная обложка, демонстрационная маркировка |
| Группа | Программа, расписание, возрастные условия, длительность, ёмкость, стоимость и период абонемента |
| Обращение | Тип «подбор» / «конкретная группа», источник, синтетический контакт, возраст, интересы, дни, текущий этап, первоначальный выбор и предложенные варианты |
| Согласованный выбор | Конкретная группа и факт явного выбора родителем; первоначальная заявка на конкретную группу уже содержит такое намерение |
| Запись на место | Связь обращения с группой, состояние «бронь», «оплачено» или «отменено», согласованная стоимость |
| Демонстрационная оплата | Связь с записью, сумма, дата, оплаченный период; одно действие не создаёт несколько оплат |
| История | События обращения: создание, контакт, предложение, выбор, бронь, оплата, отмена, закрытие с причиной |

Суммы хранятся целыми копейками; цена фиксируется в момент брони. Сведения в истории и оплаченных записях не переписываются задним числом при изменении текущей цены группы.

Тип обращения, источник и этап — разные поля. Например: «Нужен подбор» / «Форма подбора» / «Новая». Обращение через обычную форму не маркируется как AI-подбор.

Для демонстрационного набора предлагается семь синтетических программ и несколько групп: робототехника, дизайн и анимация, научная мастерская, театр, шахматы, английский и фотография. Это не перечень реальных услуг школы. Сохранить примеры трёх одобренных программ; остальные оформить с сопоставимой художественной проработкой. Нужны свободная, заполненная группа, последнее свободное место и сочетания фильтров без результата. Итоговые счётчики считаются по полному набору, а не фиксируются числами с макетов.

Начальный период и даты демонстрационных платежей задаются явно; набор воспроизводим. Период фильтрации поступлений не должен произвольно менять текущую ёмкость группы.

### Обязательные правила

1. Новое обращение и беседа с помощником не занимают место и не создают поступление.
2. Для подбора администратор сначала предлагает варианты; родитель выбирает один в представлении статуса. Только затем доступна бронь. Для прямой заявки намерение родителя уже относится к указанной группе.
3. Свободно = ёмкость − активные брони − оплаченные места. Значение не может стать отрицательным.
4. Бронь допустима только для согласованной группы с подходящими условиями и свободным местом. Повторное действие над тем же обращением не списывает ещё одно место.
5. Оплата доступна для существующей брони; перевод в оплату не занимает второе место. Повторный клик не добавляет денег.
6. Отмена неоплаченной брони освобождает место. Возвраты оплаченных записей не включаются в демо, и кнопка закрытия не должна незаметно отменять оплаченную запись.
7. Если после предложения последний слот заняла другая заявка, бронь заново проверяет ёмкость, объясняет отказ и предлагает вернуться к вариантам.
8. У формы есть устойчивый идентификатор попытки. Повторное нажатие/повторная обработка той же отправки возвращает уже созданное обращение. Новое обращение создаётся отдельным намеренным действием, не каждым открытием подтверждения.
9. Изменение выбранной группы после брони не выполняется молча: сначала отмена неоплаченной брони, затем новый согласованный выбор. Оплаченную запись нельзя таким способом переносить.
10. Закрытие обращения содержит причину. До освобождения активной брони закрытие не должно скрывать занятое место. Родительский статус соответствует действительному этапу.

Для показа исходного примера трёх групп из макетов: 12 = 7 оплачено + 2 брони + 3 свободно; 10 = 6 + 1 + 3; 10 = 8 + 2 + 0. Поступления 7 × 4 800 + 6 × 5 200 + 8 × 4 400 = 100 000 ₽. При добавлении других групп общие итоги пересчитываются, поэтому макетные значения не являются константами интерфейса.

## 4. Локальное хранение и границы демо

- Данные сохраняются одной версионированной структурой в localStorage под собственным ключом `vector-club-demo:v1`. Актуальная структура — версия 2; версия 1 мигрирует без потери обращений, броней, оплат и описаний. Готовые обложки — файлы в `public/media/`; загруженная пользователем обложка предварительно уменьшается до 1600×1200 и преобразуется в WebP, затем сохраняется строкой данных вместе с программой. Крупные изображения отклоняются; ошибка квоты браузера явно показывается.
- Родительский режим и админка используют одно состояние в одной вкладке. Переключатель режима сохраняет понятный контекст и не является контролем доступа.
- После перезагрузки валидное состояние восстанавливается. При несовместимой версии или повреждении данных не показывать ложный успех: предложить восстановление исходного демо. При ошибке сохранения сообщить, что изменения не удалось сохранить.
- «Сбросить демо» восстанавливает целиком исходные программы, группы, обращения, записи, оплаты, историю, черновики и настройки фильтров. Закрывает устаревшие подробности, переводит на существующий экран, очищает демонстрационные идентификаторы отправки. Сбрасывается только ключ Club, не весь localStorage браузера и не данные других продуктов.
- В этом объёме нет общего сервера, синхронизации между устройствами, настоящих пользователей и многопользовательских конфликтов. Обычная демонстрация проходит в одной вкладке с переключением режимов; работу школы в нескольких устройствах так не моделировать.
- Формы заранее заполнены вымышленными сведениями и контактами `example.test`. Ничего не отправляется школе, модели или платёжной системе. Проверяются возраст, обязательный контакт и корректность выбора группы; реальные сведения для показа не нужны.

## 5. Итоги и прогноз

Поступления за выбранный период — сумма демонстрационных оплат с датой в этом периоде. Это не прибыль. Загруженность и места вычисляются для соответствующих групп из действующих записей.

Прогноз размещается отдельно и маркируется «Сценарный прогноз»: пользователь задаёт, сколько дополнительных свободных мест предполагается оплатить за один выбранный период. Для разных цен выбор делается по группам; число предполагаемых мест ограничено фактическими свободными местами в этих группах. Потенциальные поступления = сумма предполагаемых оплат по выбранным группам. Изменение прогноза не создаёт заявок, броней, фактических оплат или измеренного спроса.

Прибыль, маржинальный вклад, конверсию визитов и гарантированный рост не показывать: для них пока нет согласованных исходных данных. Реальные расходы на AI и его возможную пользу считать позднее отдельным расчётом.

## 6. Независимая папка и запуск

Внутри Club созданы собственные конфигурация, зависимости и каталоги `src/`, `public/`, `tests/`, `dist/`; материалы `assets/`, `concepts/`, `references/`, `research/` сохранены.

Команды из папки Club: `npm run dev`, `npm run build`, `npm run typecheck`, `npm run test`, `npm run test:e2e`. Установка, проверки и запуск выполнены; пользователю для просмотра вводить команды не нужно.

Фактический запущенный адрес: `http://127.0.0.1:5195/`. Предложенный ранее 5193 к моменту запуска оказался занят. Сервер Club работает на loopback со строгим портом; чужие процессы не останавливались. Доступность подтверждена HTTP 200. При будущем запуске проверить владельца порта заново, не останавливать чужой сервер.

Никакого общего Hub, импорта данных соседних продуктов, настройки корневых зависимостей, установки Figma или публичного деплоя.

## 7. Порядок реализации после разрешения

1. Подготовить настоящие ассеты обложек без UI-текстов, точный PNG и локальную типографику. Создать работающий родительский каталог по утверждённой композиции. Снять реальный браузерный скриншот и сравнить с макетом.
2. Подключить программу, группу, обе формы, получение и статус обращения к общим бизнес-операциям. Затем добавить админку, предложение вариантов, бронь, оплату и отмену.
3. Добавить группы, итоги, отдельный прогноз, сохранение и полный сброс. Показать статичный помощник с работающими открытием, закрытием и переходом к форме.
4. Проверить правила и полные сценарии в настоящем браузере, мобильный родительский экран и клавиатуру. Исправить найденные дефекты, сравнить реальные изображения с согласованными макетами и оставить проверенный localhost для показа.

### Проверки готовности

- Каталог: объединённые фильтры, сброс, отсутствие результата и доступное следующее действие.
- Прямая заявка: выбор сохранён в форме, обязательные поля/ошибки, однократное создание, статус и появление в админке.
- Подбор: обращение без группы, предложение, выбор родителем, затем бронь.
- Места: новая заявка без списания; бронь минус одно; оплата без второго списания; отмена неоплаченной брони освобождает ровно одно.
- Заполненная группа и последний слот: отказ с объяснением, повторная проверка перед бронью, невозможность перебронирования.
- Оплаты: поступления меняются только после отдельной оплаты и в правильном периоде; повторная оплата не дублируется; прогноз не меняет фактические показатели.
- Состояние: перезагрузка, переходы между ролями и назад/вперёд, отсутствие устаревшего выбранного обращения после сброса, повторный полный прогон.
- Помощник: пример диалога честно маркирован; нет активного свободного ввода или запроса к модели; открытие/закрытие и восстановление фокуса работают; формы доступны без помощника.
- Внешний вид и доступность: 16:10 (ориентир 1440×900 без заявления о реальном разрешении ноутбука), мобильный экран 390×844, отсутствие горизонтальной прокрутки, клавиатурный фокус, подписи полей, ошибки, закрытие панели Escape и возврат фокуса.
- После согласования версии: build, typecheck, проверки бизнес-правил, браузерные сценарии и визуальная сверка отдельно. Успешная сборка не заменяет браузерные проверки.

## Результат реализации

Отдельное разрешение получено в прямом сообщении пользователя после восстановления лимита: «можешь продолжить разработку». Дополнительного согласования каждой итерации пользователь прямо просил не запрашивать. Рабочие сценарии, независимый запуск и визуальная доводка выполнены. Финальные доказательства — `qa/REVIEW.md`: сборка с TypeScript, 18 проверок логики, 24 браузерных сценария и реальные скриншоты. Продукт остаётся локальной демонстрацией с синтетическими данными; интеграции и публикация требуют отдельного поручения.
